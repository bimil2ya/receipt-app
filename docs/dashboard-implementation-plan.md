# 사무실 담당자용 집행 현황 대시보드 구현 계획

작성일: 2026-09-29  
상태: 2차 내부 검토 완료 — 이 문서를 기준으로 단계별 구현·검증·내부 검토를 진행한다.  
배포: 이 계획의 범위 밖이다.

## 1. 목적과 범위

사무실 담당자가 현장 팀이 공식 제출한 Drive 자료를 한 곳에서 확인하도록 한다. 기준은 월별 전체집계 Google Sheet와 각 팀의 정산서 PDF다. 월 집계에 반영된 사실과 모든 최종 산출물이 확인된 최종 제출 완료는 별도 상태로 취급한다.

- 조회 기준: 월 전체, 팀별. 개인별 조회는 제공하지 않는다.
- 확인 내용: 총액·용도별 합계·영수증 건수·팀별 검토 현황·전체내역·팀 정산서 PDF.
- 접근 경로: 현장 앱과 분리된 같은 프로젝트의 `#/dashboard` 웹 화면이다. 현장 앱의 제출·자동 진행 공유·완료 횟수에는 영향을 주지 않는다.
- 이 단계는 데이터를 읽어 보여 주는 기능이다. 검토 결과를 수정하거나 현장 앱에 다시 반영하는 쓰기 기능은 별도 단계다.

## 2. 확인된 사실

1. `src/main.jsx`는 `#/dashboard`에서 `src/dashboard/*`를 지연 로드한다.
2. `api/dashboard.js`는 인증, 월 데이터, 정산서 PDF 요청을 하나의 기존 API 경로에서 처리한다.
3. `api/_dashboardData.js`와 `api/_dashboardReports.js`는 현재 예시 데이터를 반환한다. 따라서 화면은 있지만 실제 Drive 자료가 연결되어 있지 않다.
4. 공식 월 집계는 기존 `getYearMonth()` 표기의 `전체집계_YYYY년 MM월` Google Sheet이며, `전체내역`, `검토기록`, `날짜별집계` 등 필수 탭과 영수증 식별값을 생성·검증하는 코드가 `api/aggregate.js`, `api/_aggregateSubmission.js`에 있다.
5. 팀 정산서는 기존 업로드 흐름에서 `메인/YYYY년 MM월/팀/주간/정산서_*.pdf` 아래에 저장된다.
6. 현장 앱의 조용한 진행 공유는 `/api/review`와 Drive의 `_진행현황`을 사용하며 공식 제출·월 집계와 분리되어 있다. 대시보드의 공식 금액 기준으로 쓰지 않는다.
7. 현재 Vercel 함수 수는 상한(12개)에 도달해 있으므로, 이 작업은 신규 API 파일을 만들지 않고 기존 대시보드 모듈 안에서 끝낸다.

## 3. 판단 근거와 미확인 가정

### 확인된 사실에 따른 결정

- 화면의 총액과 팀별 금액은 Drive의 공식 월 집계 `전체집계_YYYY년 MM월`만 기준으로 계산한다.
- 정산서 PDF는 Drive 경로, 파일명, MIME 타입을 모두 확인한 파일만 반환한다. 임의 Drive 파일 ID를 열 수 있게 하지 않는다.
- Sheet가 없거나 형식·합계가 맞지 않으면 0원 예시로 대체하지 않고 조회 실패로 표시한다. 서버와 화면 양쪽에서 필수 응답 필드·월·합계 불변식을 확인하며, 부분 응답도 정상 0원 화면으로 렌더링하지 않는다.
- 역할별 노출 차단은 화면이 아닌 서버 응답에서 처리한다. 담당자 역할에 허용되지 않은 `flags`, `coDining` 필드는 응답 객체에 넣지 않는다.

### 합리적 추정

- 담당자는 월 전체를 먼저 보고, 필요할 때 팀을 선택해 정산서와 원장 행을 대조한다.
- 정산서 PDF 표지는 팀별 용도 집계이며 이후 페이지가 원본 영수증이므로, 같은 화면의 PDF 뷰어가 대조 업무에 적합하다.

### 미확인 가정 — 코드에 고정하지 않을 것

- 담당자/소유자 역할별로 어떤 금액 이상 지출, 공동 식사 정보를 볼 수 있는지.
- 월 집계의 탭 이름·열 구성이 언제 “동결”되는지와 과거 파일의 영수증 식별값 누락 처리 기준.
- 큰 PDF(응답 본문 제한을 넘는 경우)의 전달 방식과 보관 기간.
- 향후 검토 결과를 현장 앱에 보일 범위 및 수정 버전의 승인 규칙.

이 항목은 상수나 화면 문구에 박지 않고, 데이터 매핑과 권한 정책을 교체 가능한 함수/설정으로 분리한다.

## 4. 단계별 실행 계획

### P0-A. 기준선과 계약 확정

1. 현재 `main`과 `feat/dashboard-scaffold`의 차이를 읽기 전용으로 비교한다. 현장 앱의 최신 변경을 덮어쓰거나 브랜치를 무조건 병합하지 않는다.
2. `api/dashboard.test.js`, 집계 검증 테스트, lint, build를 실행해 현재 기준선을 기록한다. Vercel 함수 수 역시 현재 산출물로 다시 측정하며, 과거 문서의 12개 수치를 사실로 가정하지 않는다.
3. 대시보드가 소비하는 payload 계약과 Sheet의 실제 필수 탭·열을 테스트로 명시한다. 실 Drive가 아닌 고정 XLSX/PDF fixture와 Drive 경계 주입을 사용해 계약 테스트가 환경변수·운영 자료에 의존하지 않게 한다.
4. 화면도 필수 payload 필드, 응답 `month`, 역할, 합계 불변식을 검증한다. 빠진 필드·틀린 월·불일치 합계는 전체 조회 실패로 처리하는 테스트를 추가한다.

완료 기준: 기존 대시보드 API 계약과 공식 집계 파일 계약을 문서와 테스트에서 동시에 확인한다.

### P0-B. 월별 전체집계 데이터 연결

1. `buildDashboardPayload({ month, role })`를 예시 데이터 대신 Drive의 해당 월 `메인/YYYY년 MM월/전체집계_YYYY년 MM월` export 파서로 교체한다. API 입력의 `YYYY-MM`은 기존 월 폴더 표기로 변환한다. 보관함·스냅샷·작성 중 파일은 제외하고 중복 월 폴더나 집계 파일은 실패로 처리한다.
2. `전체내역`, `검토기록`, `날짜별집계`에서 금액·분류·팀·검토 상태를 안전하게 읽는다. 금액은 안전한 정수만 허용한다.
3. 영수증 식별값으로 검토기록을 정확히 연결한다. 구형 행의 팀·날짜·사용처·금액 보조 매칭은 양쪽 후보가 정확히 하나이며 아직 다른 행에 연결되지 않은 경우에만 허용한다. 식별값 불일치, 중복 후보, 삭제된 과거 행, 수정 버전이 확인되지 않는 승인 기록은 현재 검수 완료로 추정하지 않고 `대조 불가`로 남긴다. 매칭 실패·모호함·과거 기록 건수를 숨기지 않고 반환한다.
4. 검토 상태의 자유 입력값을 `ok/req/none/unknown`으로 해석하는 정책을 분리한다. `unknown`은 완료에 포함하지 않는다.
5. 다음 불변식을 서버에서 검사한다: 원장 합계 = 총 지출, 용도별 합 = 총 지출, 핵심/유류·의료 분할 합 = 총 지출, 팀 검토 건수 ≤ 팀 영수증 건수, `날짜별집계`의 유일한 `합계` 행 = 전체내역 총액. 날짜 없는 행과 미정 분류의 금액도 누락시키지 않는다.
6. Sheet를 찾지 못함, 중복 파일, 필수 탭/열 누락, 숫자 오류, Drive 네트워크 오류는 실패로 처리한다. 예시 데이터로 성공처럼 보이지 않게 한다.
7. Drive 목록은 모든 `nextPageToken`을 읽으며, `incompleteSearch`, 다음 페이지 오류, 반복 토큰, 설정한 한도 초과를 빈 목록이나 부분 성공으로 반환하지 않는다. 조회·export·PDF 요청의 재시도와 전체 시간 한도도 테스트한다.
8. `ledger`와 `reviewsRaw`를 포함한 JSON은 UTF-8 바이트 크기를 측정한다. 응답 한도를 넘으면 잘라낸 원장을 전체 자료처럼 반환하지 않고 명시적인 조회 실패를 반환한다. 페이지 조회가 필요해지면 기존 `action=data`의 호환 가능한 확장으로 설계한다.
9. 월집계 반영 여부와 최종 제출 완료 여부를 구분한다. 읽기 전용 범위에서 완료 증거를 조회할 수 없다면 `submitted:true`를 만들지 않고 “집계 반영” 또는 “완료 확인 불가”로 표시한다.

완료 기준: 실제 Sheet의 결과가 기존 화면 계약을 충족하고, 실패 원인이 사용자에게 구분되어 보인다.

### P0-C. 팀 정산서 PDF 연결

1. 팀 이름과 월로 Drive의 `메인/YYYY년 MM월/팀/주간/정산서_*.pdf`만 찾는다. 모든 Drive 목록 페이지를 확인하고, 월 경계·동일 주간 이름·같은 팀의 복수 제출 PDF를 보존한다.
2. 반환 전 부모 경로·파일명·PDF MIME 타입을 검증하고, PDF 바이트 요청 시에도 다시 확인한다.
3. 서명된 보고서 참조값을 유지해 브라우저가 임의 Drive ID를 제출해도 열리지 않게 한다.
4. PDF가 Vercel 응답 크기 제한을 넘을 때의 실패 메시지와 이후 전달 대안을 문서화한다. 실제로 안전한 직접 열기 경로를 제공하기 전에는 존재하지 않는 Drive 경로를 안내하지 않는다. 이 단계에서 무단 외부 공개 URL을 만들지 않는다.

완료 기준: 선택한 팀의 해당 월 정산서만 열리고, 다른 경로·형식의 파일은 거부된다.

### P1. 화면 실데이터 연결과 사무실 확인 흐름

1. 기존 대시보드 화면을 바꾸기보다 확정된 실데이터 계약에 연결한다. 요청 세대·로그인 세션·역할·월이 모두 현재 값인 응답만 반영하고, 캐시는 세션별로 격리한다.
2. 월 선택 → 전체 요약 → 팀 선택 → 전체내역/검토 현황 → 팀 정산서 PDF의 순서로 실제 브라우저에서 확인한다.
3. 조회 실패, 빈 월, 부분 검토, 대조 불가, PDF 없음/복수/너무 큼을 정상 상태와 구분해 표시한다. PDF와 원장 사이의 영수증 단위 연결이 실제로 없다면 연결된 것처럼 표시하지 않고, 공통 식별값·페이지 위치 제공 가능 여부를 확인한다.
4. 월을 바꿨을 때 기존 팀이 새 월에 없으면 조용히 첫 팀으로 바꾸지 않는다. 전체 선택으로 되돌리거나 변경 사실을 명시한다.
5. 현장 앱에서 `#/dashboard`로 우연히 이동해도 제출 화면 상태를 변경하지 않는지 확인한다.

완료 기준: 사무실 담당자가 팀별·전체 기준으로 자료를 비교할 수 있고, 누락 자료가 정상 자료처럼 보이지 않는다.

### P1. 검증과 내부 검토 반복

1. 단위 테스트: 정상 집계, 탭/열 누락, 중복 식별값, 금액 파싱 오류, 정확/보조 검토 연결, 과거·삭제·수정 전 검토 기록, 알 수 없는 상태, 역할별 필드 제거, 날짜 공란·미정 분류, `날짜별집계` 합계 중복/불일치, 불변식 위반, Drive 네트워크 오류.
2. Drive 테스트: 다중 페이지 정상/중복/반복 토큰, 다음 페이지 429·네트워크 오류, 목록·export·PDF 시간 초과, 월/팀/주차 필터, 경로 이탈, MIME 위조, 서명 위조, PDF 다운로드 실패, 응답 JSON의 한글 메모 포함 크기 경계.
3. 화면·브라우저 테스트: 부분 payload, 월 A→B→A 역순 응답, owner 요청 지연 뒤 staff 재로그인, 월 변경 뒤 팀 소멸, 빈/복수/대용량 PDF, 팝업 차단 가능성이 있는 인쇄 흐름.
4. 회귀 테스트: `npx vitest run`, `npm run lint`, `npm run build`, 필요한 현장 앱 흐름 테스트.
4. 내부 검토자는 P0·P1만 선별한다. 지적을 반영한 뒤 다시 검토하며, 추가 P0/P1이 없거나 최대 3회 후 남은 이견을 기록한다.

완료 기준: 실패를 성공으로 표시하는 경로와 다른 팀/파일 노출 경로가 테스트로 차단되고, 기존 제출·집계 테스트가 통과한다.

## 5. 작업 순서와 변경 경계

1. P0-A → P0-B → P0-C → P1 화면 확인 → P1 검증/검토 순서로 한 단계씩 완료한다.
2. 각 단계 시작 전 관련 코드·테스트·화면·데이터 호환성·완료 기준을 다시 확인한다.
3. 신규 서버 원장, 새 로그인 체계, 새 Drive 데이터 구조는 이 범위에 넣지 않는다.
4. 기존 Drive 자료나 Google Sheet를 파괴적으로 변환하지 않는다.
5. 배포와 Vercel 환경변수 설정은 별도 요청이 있을 때만 진행한다.

| 파서 구현, API 테스트, 회귀 수정 | GPT-6 Sol (high) | 구현과 테스트 반복에 적합하다. |

토큰을 아끼려면 Astra는 P0 착수·내부 검토·최종 판정에 집중하고, 중간 구현과 반복 검증은 Sol로 수행한다. 모델 전환은 현재 Codex 대화에서 제가 직접 실행할 수 없으므로, 전환이 유리한 단계가 오면 시작 전에 권장 모델을 분명히 알린다.
