# 출장 영수증 제출 신뢰성 개선 (2026-09-07)

## 범위와 근거

사용자 지시를 제품 문서보다 우선했다. 시작 시 git 작업 트리는 깨끗했다. 배포와 실서비스 Drive 쓰기/알림 발송은 수행하지 않았다. 실제 개인 브라우저 DB는 조회하지 않았으며, 코드·기존 테스트·격리된 브라우저 테스트 데이터로 검증했다. 기존 데이터 전체가 정상이라고 판단한 것은 아니다.

### 확인된 사실

- 사용자는 현장 사업자와 사무실 담당자이며, 종이 업무에서는 집계표와 원본을 대조했다(사용자 설명).
- 입력 → `useReceiptCrud` → IndexedDB `receipts`/`receipt_images` → 집계 화면 → `useDriveUpload` → XLSX/사진/PDF → `/api/upload` → Drive 및 월 집계 순서다.
- IndexedDB 스키마는 v8이다. 이번 변경은 스키마·저장 데이터·XLSX 열·API 요청 형식을 변경하지 않는다.
- XLSX 요청에서 월 집계와 카카오 알림이 먼저 실행되고, 사진과 PDF는 후속 요청이다. 전체 제출을 원자적으로 확정하는 서버 단계는 없다.
- 기존 업로드 코드는 XLSX 실패를 기본 ‘완료’, 집계 응답 부재를 ‘집계 완료’, 사진 HTTP/통신 오류를 성공 건수로 취급했다.
- 이미지 ID는 있지만 실제 Blob이 없으면 기존에는 사진을 누락한 채 진행했다.
- 화면 용도별 집계는 정해진 5개 분류만, 일자별 집계는 날짜가 있는 항목만 표시했다. PDF 표지는 모든 분류·항목을 합산하므로 차이가 발생했다.
- `uploadSendCount`와 `kakaoSendCount`는 과거 전송 횟수다. 현재 자료 버전이나 사무실 수신·검수 결과를 증명하지 않는다.
- 중복 판정은 승인번호 기반 후보 보고다. 중복 자동 삭제나 지출 불인정 규칙을 추가하지 않았다.

### 합리적 추정

- 담당자는 누락된 원본과 전송 실패를 알 수 있어야 한다.
- 분류·날짜가 불완전해도 항목은 집계에서 사라지면 안 된다.
- 전송 이후 자료 수정 여부와 사무실 검수 여부를 구별할 필요가 있다.

### 미확인 가정과 처리

- 사진 없는 수기 항목을 허용할지, 어떤 증빙을 요구할지: 기존 수기 입력 허용 동작 유지. 사진 참조가 깨진 경우만 제출 전 중단한다.
- 승인번호 없는 현금 영수증, 환불/취소, 분류별 인정 한도와 출장기간 밖 지출의 처리: 새 차단·삭제·재분류 규칙을 도입하지 않았다.
- 공식 담당자/단체방: 특정 개인·방을 하드코딩하지 않고 `SummaryTab.shareRecipientGuidance` prop으로 교체 가능하게 했다. 기본값은 중립적 선택 안내다.
- 출장 마감에 필요한 승인 절차: 승인 상태를 신설하지 않았다. 전송 이력과 실제 수신·검수는 구분해 안내한다.
- 기존 분류 순서와 소계 대상은 코드에서 확인한 동작이므로 유지했다. 미등록 분류는 원래 이름으로 추가 표시하며, 기존 빈 분류의 ‘기타’ 표시도 유지한다. 저장된 분류 자체는 바꾸지 않는다.

## 구현

- P0: XLSX는 HTTP 성공과 `success: true`, `fileId`를 확인한다. 집계는 명시적인 성공 응답만 인정한다. 사진은 해당 파일명이 성공/중복 목록에 있어야 인정한다. PDF는 `success: true`와 `assembled: true`를 요구한다.
- 집계는 `fileId`와 정수 `count`까지 확인한다. 서버는 월내 XLSX 원본을 하나라도 읽지 못하면 기존 집계 파일을 교체하지 않고 실패한다. PDF는 `fileId`와 허용된 `uploadStatus`까지 확인한다.
- 실패 사진을 재시도 목록에 저장하고 최초 팀·출장기간·보고일을 함께 보존한다. 취소 또는 원본 사전 점검 실패로 기존 재시도 목록을 지우지 않는다. 재전송도 응답 본문을 확인한다.
- XLSX·집계·PDF가 확인된 제출의 실패 사진만 재시도해 모두 성공하면 완료 횟수를 정확히 한 번 반영한다. 최근 완료 지문 20개를 별도 localStorage 키에 저장해 빠른 연속 탭, 재마운트, A→B→A 반복 완료를 막는다. 기존 전송 횟수 저장 형식은 바꾸지 않는다.
- 이미지 조회 실패·빈 Blob·FileReader 오류를 명시적으로 처리한다. 수기 항목의 이미지 미첨부와 깨진 이미지 참조를 구별한다.
- 팀 관리자 인증 미설정 경로의 누락된 `createError` import를 수정했다. 기존 테스트가 재현한 실제 ReferenceError다.
- 브라우저 회귀 검사 중 발견한 전송 횟수 복원 문제도 수정했다. 초기 렌더/팀 전환 시 읽기 effect와 저장 effect가 함께 실행되어 저장값이 이전 상태로 덮일 수 있었다. `loadedStorageKey`가 현재 키와 일치할 때만 저장하도록 보호했다.
- P1: 미등록 분류를 추가 표시하고 날짜 없는 그룹을 ‘날짜 없음’으로 표시한다. JSX의 추가 필터에서도 미등록 분류를 제거하지 않는다.
- P2: ‘출장 마감 완료’를 ‘전송 이력이 있습니다’로 바꾸고 수정 자료 재전송·수신/검수 별도 확인을 안내한다. 특정 수신자 안내를 교체 가능한 prop으로 분리했다.

- 외부 업로드/API는 고정 응답으로 격리한다. 실제 Drive/월 집계/카카오의 원격 성공을 검증했다고 주장하지 않는다.

## 남은 위험과 권장 순서

1. **P0 후속:** 서버 제출 확정 단계가 없어 응답 유실 시 클라이언트는 서버 처리 여부를 증명할 수 없다. 재실행하면 Drive 파일은 이름 기준 교체되지만 알림이 중복될 수 있고, 여러 탭·기기의 동시 제출은 로컬 지문으로 막을 수 없다. 이를 완전히 해결하려면 서버 원장에 `batchId`/멱등키, 산출물별 상태, 최종 완료를 저장하고 알림을 최종 단계에서 한 번만 보내야 한다. 예상 범위는 API 계약, 영속 저장소, 업로드/집계/알림 순서, 복구 UI와 통합 테스트다. 이번 최소 변경에는 포함하지 않았다.
2. **P1 후속:** PDF에 수기 항목 상세와 XLSX/사진을 연결하는 공통 검수 번호가 없다. 담당자 검토 후 부가 열·상세 페이지를 추가하고 실제 PDF 페이지 렌더링까지 검증할 것.
3. **P1 후속:** 재시도 목록은 메모리 상태라 새로고침하면 사라진다. 전체 업로드로 재확인할 수 있지만 영속 재시도·제출 스냅샷이 필요하다. 기존 과거 전송 횟수에는 이전 버전의 오판정이 남을 수 있어 이력으로만 표시한다.
4. **P1 후속:** 기본 테스트 실행의 기존 3개 실패를 정리하고 실서비스 통합 테스트는 명시적인 별도 실행으로 분리할 것. 운영 검증에는 별도 테스트 Drive 폴더와 알림 대상이 필요하다.
5. **P2 후속:** 담당자에게 현금/수기 증빙, 중복 판단 예외, 인정 분류, 제출 수정/반려/승인 절차를 확인한 뒤 버전 있는 정책 설정으로 구현할 것. 현재 자료만으로 확정하지 않는다.

## P2 검토기록 시트 기반 (2026-09-10)

### 확인된 사실

- 월별 `전체집계_YYYY년MM월`은 새 제출 때마다 새 Google Sheet로 교체된다.
- 영수증 XLSX에는 새 항목부터 `영수증식별값`이 포함되며, 이 값은 담당자 검토 기록을 다시 연결할 수 있다.

### 구현

- 월별 전체집계에 `검토기록` 시트를 추가했다. 영수증 식별값, 팀, 원본 항목 정보와 담당자 입력 열(`검토 상태`, `담당자 메모`, `추가 자료 요청`, `검토 담당자`, `검토 시각`)을 함께 제공한다.
- 다음 집계 전에 기존 Google Sheet의 `검토기록`을 XLSX로 내보내어 같은 식별값의 담당자 입력 열을 병합한다. 새 원본에서 사라진 기존 행도 자동 삭제하지 않는다.
- 상태 값의 목록, 승인·반려의 의미, 재제출 규칙은 아직 확정하지 않았으므로 자유 입력 열로 유지한다.

### 한계와 다음 작업

- 현재 앱은 아직 `검토기록`을 읽어 팀별로 표시하지 않는다. 이 시트는 사무실 기록을 보존하는 첫 단계다.
- Google Drive API 실제 계정으로 내보내기·병합 동작은 실행하지 않았다. 단위 테스트는 Drive 응답을 격리하므로, 운영 도입 전 별도 테스트 Drive 폴더에서 검증해야 한다.

이번 변경의 검증 범위를 앱 전체 업무 완성 또는 운영 배포 준비 완료와 동일시하지 않는다.
